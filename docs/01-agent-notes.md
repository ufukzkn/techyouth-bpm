# Agent Notes

These notes are the project memory. Update this file whenever an implementation choice affects future work.

## Fixed Decisions

- Scope: full-stack.
- Repository target: private `ufukzkn/techyouth-bpm`.
- Frontend: Next.js App Router, TypeScript, Zustand.
- Backend: .NET 8 Web API, EF Core, selectable SQLite/PostgreSQL provider.
- Default database mode: SQLite. Shared team testing can use Neon PostgreSQL through `.env.neon.local` and `scripts/run-api-neon.ps1`.
- Documentation must be kept current as code changes.
- Team split: flow-based, not layer-based.
- Frontend target is multi-screen navigation. Hash-scroll sections were only an early scaffold and should not be treated as final UX.

## Tooling Notes

- Node and npm are installed.
- .NET SDK 10 is installed and can target `net8.0`.
- Git history should stay progressive and easy to review.
- Repository documentation should avoid machine-specific paths, credentials, tokens, or private workflow details.
- Database connection strings and email provider credentials must stay in environment variables or .NET user secrets, not tracked files.
- When database schema, seed data or local startup changes, update `docs/08-local-database.md` and `scripts/run-api-local.ps1`.

## Architecture Principles

- Keep API calls inside a frontend service layer, not inside page components.
- Keep business logic in backend services, not controllers.
- Keep state transitions in a dedicated state machine/service so process rules are easy to change.
- Keep validation rules reusable between form start and backend validation.
- Prefer small progressive commits that match the PDF evaluation story.
- Keep `Community`, `Team` and `CommunityRole` separate: security boundary, operational group and permission bundle respectively.
- `Takimsiz` is always a virtual query result; never seed a fake team row for it.
- Team leadership is context only and must never become an authorization shortcut.

- Team management rule: `/management/teams` owns team CRUD, paged members/candidates and virtual unassigned users. SuperAdmin may choose any community; Topluluk Admin is fixed to its own. Never reuse the user/community management view or load an entire community membership list in the browser.
- Team membership rule: users may join multiple teams, but only within their active community. `IsLead` is display context only. Team add/remove/lead changes require audit plus target-user notification; a community move deactivates old team memberships.
- Team loading rule: first team/list loads use shared skeletons, cached refresh keeps content and shows a small spinner, and counts use inline loaders. Mutation feedback belongs to the card that initiated it.
- Team roster rule: `/teams` is a personal read-only view. An active member may inspect only rosters of teams they currently belong to, and the roster DTO must not expose email, sessions or audit data. `/management/teams` and user-detail membership mutations remain protected by `Teams.Manage`.
- User-detail team rule: SuperAdmin may manage memberships for any community user; Topluluk Admin may manage only users and teams in their own community. Reuse the existing team member mutation endpoints and load the selected user's memberships on demand instead of expanding every user-list query.
- Dynamic definition rule: `FormDefinition` and `ProcessDefinition` are logical identities. Published versions are immutable; editing a published version creates a new draft, and running processes remain pinned to their original version IDs.
- Workflow editor rule: `/workflows` uses `@xyflow/react` for Start, User Task, Exclusive Gateway, End and Team Swimlane nodes. React Flow state is converted through `apiGraphAdapter`; never post editor-only state directly to the API. The editor supports normal, wide and full-screen modes, refits after layout changes, and returns to normal with Escape.
- Workflow SLA rule: User Task SLA is stored as nullable minutes in graph JSON. Hour/day is only an inspector presentation choice. Every new task attempt calculates its own nullable `DueAt`, including attempts created after `SendBack`.
- Gateway rule: condition paths must come from published form fields and use `start.*` or `steps.<nodeKey>.*`. A task output may be referenced only when that task precedes the gateway in the forward graph; operators and JSON values must match the referenced field type. Arbitrary JavaScript/expression execution is forbidden. Non-SendBack graph cycles are rejected and automatic routing has a 100-hop limit.
- Send-back rule: completed step history remains immutable, a new attempt is created for the target task and `steps.*` variables from the target onward are cleared so a repeated gateway cannot read stale outputs.
- Dynamic runtime rule: `DynamicWorkflowEngine` navigates graph nodes while `ProcessStateMachine` owns lifecycle statuses. Process start and task action each persist business state, step history, notifications and audit atomically.
- Assignment rule: direct assignments do not need claim. Team, community-role and team-plus-role assignments are candidate pools; the intersection is resolved server-side and only users with `Tasks.Act` qualify. `ClaimVersion` prevents two stale clients from winning one claim.
- Task-form contract: task list/detail DTOs embed the immutable published `taskForm` snapshot. `TaskActionDialog` renders and validates it for UX, but `TaskService` must always validate submitted `formData` again before graph progression and store output under `steps.<nodeKey>`.
- Demo workflow rule: the deterministic seed includes `Transfer Talep Akisi` with Scout, Technical Review, conditional Finance and Transfer Operation task forms. Keep its high-budget condition on `start.bonservis` and ensure at least one eligible candidate exists in every seeded pool.
- Demo scenario rule: each of the five seed communities also has a published versioned workflow with six coherent process examples and three open tasks. Seed task outputs must use the bound form's real field keys. Only the explicit fourteen legacy `cccc...` process IDs may be replaced; never delete user-created processes by broad status/form queries.
- Process/task list rule: both APIs are server-paged (default 10, maximum 50). Cache keys include user, filters, sort and page. A task deep link resolves its own process; the UI must never fall back to an arbitrary first process.
- Workflow visibility rule: dashboard and process lists default to `personal`; `community` requires `Processes.ViewAll`, and `global` requires SuperAdmin. `Islerim` never broadens beyond direct, claimed or live team-plus-role candidate work. Management authority alone is not task assignment.
- Workflow cache rule: frontend process/task page keys include user and scope, and all process caches are cleared when the session expires, logs out or changes to another user.
- User-detail team rule: the team-membership disclosure starts closed, resets when the selected user changes and does not call its APIs before the first open.
- Escalation rule: `Escalated` is entered by an explicit task action. `DueAt` supports deadline display and ordering; no automatic SLA escalation worker exists yet.
- Audit read rule: search, filter, pagination, scope selection and disclosure actions do not write audit records. Process start, definition publish, task claim/release/action and team-membership mutations remain auditable.
- Deterministic visibility demo: Okan starts with zero personal process/task; the seeded starter sees five owned Sportif Faaliyetler processes; Fatih sees one personal Transfer Operasyon task and six community processes; Approver and Quaresma each see two Teknik Degerlendirme candidate tasks.
